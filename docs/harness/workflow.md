# เวิร์กโฟลว์การทำงานกับ AI Agent

งานใหม่ทุกชิ้นผ่าน 7 ขั้นนี้ตามลำดับ AI ห้ามข้ามขั้น และต้องหยุดรอคนในจุดที่กำหนด

งานก่อน T-001 เกิดขึ้นก่อนมีเวิร์กโฟลว์นี้ จึงไม่มี Ticket หรือ commit `red` และ `green` ไฟล์เหล่านั้นไม่ได้สร้างย้อนหลัง

| ขั้น | ทำอะไร                                                           | หลักฐาน                       | ใครหรืออะไรคุม       |
| ---- | ---------------------------------------------------------------- | ----------------------------- | -------------------- |
| 1    | **Ticket:** ผูกงานกับรหัส requirement                            | `tickets/T-NNN-*.md`          | กฎใน `CLAUDE.md`     |
| 2    | **Contract:** ขอบเขต ไฟล์ที่แก้ได้ Definition of Done ความเสี่ยง | ส่วน Contract ใน Ticket       | **หยุดรอคนอนุมัติ**  |
| 3    | **Red:** เขียนเทสต์ที่ล้มเหลว                                    | commit `red(...)` และผลที่ล้ม | Hook                 |
| 4    | **Green:** เขียนโค้ดเท่าที่จำเป็นให้เทสต์ผ่าน                    | commit `green(...)`           | Hook                 |
| 5    | **Gate:** รัน `pnpm gate` เต็มรอบ                                | ผลใน Handoff                  | Hook                 |
| 6    | **Review:** รีวิวโค้ดแล้วแก้ findings ตามที่คนเลือก              | รายการ findings ใน Handoff    | คน                   |
| 7    | **Handoff:** สรุปงาน อัปเดต `STATUS.md` แล้ว commit              | `handoffs/T-NNN.md`           | **คนตัดสินงานถัดไป** |

## จุดที่ต้องหยุดรอคน

1. **หลังขั้น 2:** ยังไม่เขียนโค้ดจนกว่าคนจะอนุมัติ Contract ให้บันทึกผู้อนุมัติและวันที่ใน Ticket
   แล้วใส่ Ticket, วันที่อนุมัติ และไฟล์ที่แก้ได้ใน `docs/harness/state.json` ซึ่ง hook อ่าน
2. **หลังขั้น 6:** คนเลือกว่าจะแก้ findings ข้อไหน
3. **หลังขั้น 7:** คนตัดสินว่าจะทำงานถัดไปหรือไม่ การ push และ merge ต้องสั่งทุกครั้ง

## กฎของ Red และ Green

- Commit `red` ต้องมีไฟล์เทสต์ใน staged และเทสต์ต้องล้มเหลวด้วยเหตุผลที่ถูกต้อง ให้คัดลอกผลที่ล้มลงใน Ticket
- Hook ปฏิเสธ `red` ถ้า `state.json` ไม่มีวันที่อนุมัติ
- ถ้าเทสต์ต้องอ้างถึงโค้ดที่ยังไม่มี ให้สร้างโครงที่ `throw` ว่ายังไม่ได้เขียน แทนการปล่อยให้ import ล้ม
  แต่ละเทสต์จึงล้มแยกกันด้วยเหตุผลของตัวเอง ไม่ใช่ล้มทั้งไฟล์ และ `pnpm typecheck` ใน pre-commit ยังผ่าน
- Commit `green` ต้องต่อจาก `red` หรือ `green` เท่านั้น และแก้เฉพาะไฟล์ใน `files` ของ `state.json` ซึ่ง hook อ่านจาก HEAD จึงต้อง commit `state.json` ไปกับ `red`
- Commit `red` และ `green` ห้ามใช้ `-a` หรือระบุชื่อไฟล์ท้ายคำสั่ง ให้ `git add` ก่อนแล้ว commit เฉพาะที่ stage ไว้
- เมื่อจบ Handoff ให้ตั้ง `step` เป็น `done` และล้าง `approved` กับ `files` เพื่อไม่ให้การอนุมัติเก่าใช้กับงานใหม่
- Commit ปกติถัดไป เช่น Handoff ต้องผ่าน gate เต็ม งานจึงจบบน `green` ที่ยังไม่ผ่าน gate ไม่ได้
- ทั้งสองขั้นต้อง `git add` แยกคำสั่งก่อน `git commit` เพราะ hook ตรวจไฟล์ใน staged ก่อนคำสั่งจะรัน

## ถ้าต้องออกนอก Contract

หยุดแล้วบอกคน อย่าแก้เกินขอบเขตเอง ถ้าคนเห็นด้วยให้แก้ Contract และบันทึกเหตุผลไว้ก่อนทำต่อ

## สิ่งที่เครื่องบังคับไม่ได้

Hook ตรวจรูปแบบ commit, ผล gate, การบันทึกการอนุมัติ และขอบเขตไฟล์ของ `green` ส่วนเรื่องต่อไปนี้ยังอาศัยวินัยและคนตรวจ:

- เทสต์ใน `red` ล้มจริงหรือไม่ และล้มถูกเหตุผลหรือไม่
- คนอนุมัติจริงหรือไม่ เพราะ AI แก้ `state.json` เองได้ คนจึงต้องดูว่า `approved` ตรงกับ Ticket
- `files` ใน `state.json` ตรงกับ Contract หรือไม่
- Commit ปกติหลัง `green` เช่นงานเอกสาร ไม่ถูกตรวจขอบเขต แต่ต้องผ่าน gate เต็ม
