# Harness workflow ของโปรเจกต์นี้

สรุปว่าโปรเจกต์ CMS นี้ใช้ AI agent (Claude Code) ทำงานจากสเปก 9 ไฟล์อย่างไร และอะไรเป็นตัวคุมไม่ให้ผลงานออกนอกทาง

**Harness** ในความหมายนี้คือทุกอย่างที่อยู่รอบตัว AI เพื่อให้ผลงานเชื่อถือได้ ได้แก่ บริบทที่มันอ่าน กฎที่มันต้องทำตาม
การตรวจอัตโนมัติ และจุดที่คนต้องตัดสินใจ หลักคือไม่เชื่อคำบอกของ AI แต่เชื่อผลตรวจที่รันได้จริง

งานใหม่ทุกชิ้นต้องทำตาม[เวิร์กโฟลว์ 7 ขั้น](workflow.md) โดยมี [Ticket และ Contract](tickets/) ก่อนเริ่ม และ [Handoff](handoffs/) เมื่อจบ
สถานะล่าสุดอยู่ที่ [STATUS.md](STATUS.md)

## รอบการทำงานของเฟส 0–8

งานช่วงนี้เกิดก่อนมีเวิร์กโฟลว์ข้างต้น แบ่งเป็น 9 เฟส (0–8) และทุกเฟสวนรอบเดียวกัน:

```text
สเปก → วางแผนเฟส → AI เขียนโค้ดและเทสต์ → pnpm gate ──ไม่ผ่าน──→ แก้แล้วรันใหม่
                                              │
                                             ผ่าน
                                              ↓
                                         commit (git hooks ตรวจซ้ำ)
                                              ↓
                                         code review → แก้ findings → pnpm gate → commit
                                              ↓
                                         คนตัดสินใจว่าจะไปเฟสถัดไปหรือไม่
```

| เฟส | งาน                                            |
| --- | ---------------------------------------------- |
| 0   | Monorepo, TypeScript strict, gate, CI          |
| 1–2 | Auth, Users, RBAC, Audit log                   |
| 3–5 | Content, Media, Public API และ OpenAPI         |
| 6   | Admin SPA 10 หน้าจอ                            |
| 7   | E2E-01 ถึง E2E-10 ด้วย Playwright              |
| 8   | Docker Compose, nginx, deploy, backup, runbook |

## ส่วนประกอบของ Harness

| ชั้น               | ทำหน้าที่                       | อยู่ที่ไหน                                                  |
| ------------------ | ------------------------------- | ----------------------------------------------------------- |
| บริบท              | บอก AI ว่าต้องทำอะไร            | `AIAGENT_POC/` สเปก 9 ไฟล์                                  |
| กฎของโปรเจกต์      | AI อ่านทุกครั้งที่เริ่มงาน      | `CLAUDE.md`                                                 |
| ความจำข้ามหน้าต่าง | สถานะงานล่าสุด                  | memory ของ Claude Code (อยู่นอก repo)                       |
| การตีความสเปก      | บันทึกเหตุผลเมื่อสเปกขัดกัน     | `docs/adr/` โดยเฉพาะ `0013-spec-conflicts.md`               |
| กฎสถาปัตยกรรม      | ห้ามเขียนผิดโครงสร้าง           | `eslint.config.mjs`, `tools/eslint/`, `.dependency-cruiser` |
| Quality gate       | ตรวจก่อน commit 18 ขั้น         | `tools/gates/run-gate.mjs`, สถานะใน `docs/quality/gates.md` |
| ทดสอบตัว gate เอง  | ฝังโค้ดผิด 28 แบบ ต้องจับได้ครบ | `tools/gates/self-test.mjs`                                 |
| Claude Code hook   | กันคำสั่งของ AI ก่อนรันจริง     | `.claude/settings.json`, `tools/gates/git-guard.mjs`        |
| Git hooks          | กันที่ commit และ push          | `.husky/`                                                   |
| ตรวจระบบจริง       | รันทั้งระบบ ไม่ใช่แค่ unit test | `cms-web/test/e2e/`, `infra/scripts/smoke-*.sh`             |
| คน                 | อนุมัติเฟส ตัดสินใจเรื่องสำคัญ  | ไม่ push หรือ merge จนกว่าจะสั่ง                            |

Gate 18 ขั้นครอบคลุม format, TypeScript, lint, สถาปัตยกรรม, requirement traceability, coverage, mutation, duplication, secret scan, bundle,
E2E, CVE และ license ส่วน test-to-code ratio ยังถูกข้ามเพราะไม่มี `origin/main` ให้เทียบ

Claude Code hook ตรวจทุกคำสั่ง shell ของ AI ก่อนรัน โดยมีกฎ 5 ข้อ:

| คำสั่ง                                  | ผล                                                       |
| --------------------------------------- | -------------------------------------------------------- |
| `git commit` ที่ไม่ผ่าน gate เต็มล่าสุด | ปฏิเสธ และบอกว่าไฟล์ไหนเปลี่ยนหลัง gate ยกเว้นไฟล์ `.md` |
| ข้าม git hook เช่น `--no-verify`        | ปฏิเสธเสมอ                                               |
| `git push`                              | ต้องให้คนกดอนุมัติทุกครั้ง                               |
| `git commit` แบบ `red(...)`             | ไม่ต้องผ่าน gate แต่ต้องมีไฟล์เทสต์ใน staged             |
| `git commit` แบบ `green(...)`           | ไม่ต้องผ่าน gate แต่ต้องต่อจาก `red` หรือ `green`        |

กฎนี้ถูกเพิ่มเพราะ "รัน gate ก่อน commit" เคยเป็นแค่ข้อตกลง และเคยมีครั้งหนึ่งที่ commit ไปก่อน gate จะผ่าน

## ตัวอย่างที่ Harness จับได้จริง

| เหตุการณ์                                                       | ใครจับได้           | ผล                                           |
| --------------------------------------------------------------- | ------------------- | -------------------------------------------- |
| AI ทำให้ `prisma` กลายเป็น production dependency ที่ผิด license | License gate        | ไม่ commit และบันทึกให้ Tech Lead ตรวจ       |
| โค้ด heartbeat ใหม่ทำ worker ล้มบน Windows                      | E2E                 | แก้ก่อน commit                               |
| ตัวตรวจ placeholder ไปอ่านบรรทัด comment จน deploy ไม่ได้       | การซ้อม deploy      | แก้สคริปต์                                   |
| backup ไม่เคยลบ snapshot เก่า ทั้งที่สคริปต์รันผ่าน             | Code review         | แก้แล้วเพิ่มการตรวจจำนวน snapshot            |
| Postgres ถูกสร้างใหม่ทุกครั้งที่ deploy                         | Code review         | แก้แล้วยืนยันว่า container ID ไม่เปลี่ยน     |
| Editor พังเฉพาะตอน production build                             | การรันบน build จริง | ผ่าน gate อื่นหมด จึงเพิ่ม E2E บน build จริง |

## ข้อจำกัดที่ควรพูดเอง

- **Hook มีช่องโหว่:** ตรวจจากข้อความของคำสั่ง ถ้า `git commit` อยู่ในไฟล์สคริปต์จะมองไม่เห็น และคนที่ commit เองนอก Claude Code จะไม่ผ่าน hook นี้
- **Hook เพิ่งเพิ่มตอนท้าย:** ใช้กับงานจากนี้ไป ส่วน commit ก่อนหน้าทำตามข้อตกลงโดยไม่มีตัวบังคับ
- **ไม่มีหลักฐาน TDD ของเฟส 0–8:** ไม่มี commit `red` หรือ `green` จึงยืนยันไม่ได้ว่าเขียนเทสต์ก่อนโค้ด เวิร์กโฟลว์ใหม่เริ่มเก็บหลักฐานตั้งแต่ T-001 โดยไม่สร้างของเก่าย้อนหลัง
- **เวิร์กโฟลว์บังคับได้บางส่วน:** Hook ตรวจรูปแบบ commit และ gate ได้ แต่ตรวจไม่ได้ว่าเทสต์ใน `red` ล้มจริง หรือ Contract ได้รับอนุมัติจริง
- **CI ไม่เคยรัน:** ไม่มี remote gate จึงรันแค่ในเครื่องและใน git hook
- **คนไม่ได้อ่านทุกบรรทัด:** การตรวจส่วนใหญ่มาจาก gate และ review ของ AI ส่วน AI ที่รีวิวงานตัวเองก็อาจมองข้ามจุดเดิมได้
- **ผลงานเป็น Demo:** ยังไม่เคยขึ้น VM จริงและยังไม่เคยวัด performance

## เดโมให้หัวหน้าดู

1. เปิดสเปกและ ADR-0013 เพื่อแสดงว่าเริ่มจากเอกสาร และเมื่อสเปกขัดกันมีการบันทึกเหตุผล
2. ดูประวัติ จะเห็นรอบ `feat` ตามด้วย `fix: resolve findings` แทบทุกเฟส:

   ```bash
   git log --oneline --all --reverse
   ```

3. รัน gate แบบเร็ว ซึ่งใช้เวลาราว 1.5 นาที:

   ```bash
   pnpm gate:fast
   ```

4. พิสูจน์ว่า gate จับของผิดได้จริง ซึ่งเป็นจุดที่น่าโชว์ที่สุด คำสั่งนี้ใช้เวลาราว 5.5 นาที จึงควรรันทิ้งไว้ก่อนเดโม
   แล้วเปิดผล `28/28 caught` ให้ดู:

   ```bash
   pnpm gate:self-test
   ```

5. โชว์ hook สดๆ โดยแก้ไฟล์โค้ดสักบรรทัด แล้วสั่ง Claude Code ว่า `commit เลย ไม่ต้องรัน gate` AI จะโดนปฏิเสธพร้อมชื่อไฟล์
   เสร็จแล้วสั่งให้ย้อนการแก้นั้น
6. เปิดระบบตาม [คู่มือ Demo](../demo-guide.md) เพื่อแสดงผลลัพธ์ปลายทาง

## คำถามที่น่าจะเจอ

| คำถาม                        | แนวคำตอบ                                                               |
| ---------------------------- | ---------------------------------------------------------------------- |
| ถ้า AI ทำผิด จับได้อย่างไร   | gate, E2E, การรันระบบจริง และ review พร้อมตัวอย่างจากตารางด้านบน       |
| รู้ได้อย่างไรว่า gate ใช้ได้ | `gate:self-test` ฝังโค้ดผิดแล้วต้องจับได้ครบ                           |
| AI ข้าม gate ได้ไหม          | Claude Code hook ปฏิเสธการ commit แต่ยังมีช่องโหว่ตามหัวข้อข้อจำกัด    |
| AI ลืมบริบทไหมเมื่อเปิดใหม่  | ใช้ memory เก็บสถานะและบทเรียน และเริ่มแต่ละเฟสด้วยการตรวจเทียบกับ git |
| ตรงไหนที่คนต้องตัดสินใจ      | การไปเฟสถัดไป, การเลือกแก้ findings, การ push, และเรื่อง license       |
| จุดอ่อนของวิธีนี้คืออะไร     | ตอบจากหัวข้อข้อจำกัดด้านบน                                             |
